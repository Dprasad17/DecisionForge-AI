# DecisionForge AI — Technical Decision Record & Engineering Analysis

This document provides a comprehensive record of the architectural choices, model selections, engineering trade-offs, failure mitigations, and production roadmap for **DecisionForge AI**.

---

## 1. Model Selection & Multi-Model Processing Strategy

### Approach A: Supervised Intent Classifier (Linear Probe on Dense Embeddings + TF-IDF Fallback)
- **Primary Mechanism:** Logistic Regression (`C=5.0`, `class_weight="balanced"`) trained directly on frozen 384-dimensional dense sentence embeddings generated by `all-MiniLM-L6-v2`.
- **Secondary Fallback:** Scikit-learn Pipeline with character/word TF-IDF N-grams (1,2) and Logistic Regression.
- **Why Chosen over an LLM for Classification:**
  1. **Deterministic Latency & Low Compute:** Evaluates in sub-millisecond CPU time (< 0.1 ms when query embedding is shared), compared to 500–2,000 ms for cloud-hosted LLM APIs.
  2. **Calibrated Probability Distributions:** Generates a continuous probability distribution across all 9 intent classes via `predict_proba()` (softmax over linear log-odds). This enables principled confidence-based escalation thresholds (`confidence < 0.60`) rather than binary heuristics.
  3. **Zero Financial / API Cost:** Operates fully local offline with 0 cloud API expenditures.

### Approach B: Dense Semantic Retrieval (`all-MiniLM-L6-v2`)
- **Mechanism:** L2-normalized 384-dimensional dense sentence embeddings combined with NumPy dot-product cosine similarity.
- **Why Chosen:**
  1. **Compact & Fast:** At ~90MB, `all-MiniLM-L6-v2` runs on standard CPUs with 10–15 ms latency per inference pass.
  2. **Semantic Generalization:** Accurately maps synonymous phrasing (e.g., *"cannot sign into portal"* to *"Password Reset and Two-Factor Authentication Recovery"*) where strict lexical matching fails.

### Shared Embedding Optimization (Stage 0)
- In the naive pipeline, the classifier and retriever each computed embeddings independently, doubling inference latency.
- In DecisionForge AI, Stage 0 computes the normalized query embedding once and passes it downstream to both the classifier and the retriever, eliminating 100% of redundant neural encoding.

## 2. Why Hybrid Semantic / Keyword Retrieval Was Used

Pure dense retrieval and pure keyword retrieval have complementary failure modes:
1. **Dense Retrieval Failure Mode:** Dense embeddings map queries to semantically related but procedurally incorrect documents (e.g., retrieving general account access rules instead of specific dispute procedures for a refund request).
2. **Lexical Retrieval Failure Mode:** Keyword/token overlap (e.g., Jaccard or BM25) fails completely when users use synonyms, colloquial phrasing, or non-overlapping vocabulary.

### Hybrid Fusion Formula
DecisionForge AI implements hybrid score combination:
$$\text{Score}_{\text{hybrid}} = 0.70 \times \text{Score}_{\text{dense}} + 0.30 \times \text{Score}_{\text{keyword}} + 0.05 \times \mathbb{I}(\text{Category Match})$$

### Relevance Threshold Gating (Threshold = 0.22)
- Without a relevance threshold, nearest-neighbor vector search *always* returns a top candidate, even when the query is completely unrelated to the business (e.g., *"What is the weather in Paris?"*).
- An empirical noise floor threshold of `0.22` ensures out-of-scope inquiries return zero candidate evidence, automatically triggering clarification escalation (`POL-003`).
- **Validation:** On the held-out test set, Recall@1 is invariant across thresholds `0.00` to `0.30`. The threshold was selected based on validation partition behavior where Recall@3 remains 100% up to 0.22 before dropping at 0.25.

## 3. Deterministic Policy Guardrails & Controlled Autonomy

Machine learning models are probabilistic; compliance and safety must be deterministic. DecisionForge AI decouples decision safety from model confidence through 7 deterministic policy guardrails:

| Rule ID | Name | Trigger Condition | Enforced Action | Target Status |
| :--- | :--- | :--- | :--- | :--- |
| **POL-001** | Prompt Injection Detection | Regex pattern match on adversarial overrides (`ignore previous rules`, `system prompt injection`, `root shell`, `transfer \$?\d+`, `bypass 2fa`). | Intercept request immediately; log threat signature. | `BLOCKED_BY_POLICY` |
| **POL-002** | Restricted Financial Action | Sensitive operations (`direct transfer`, `force approval`, `wire transfer`, `modify ledger`). | Block automated execution; require compliance authorization. | `BLOCKED_BY_POLICY` |
| **POL-003** | Ambiguity & Underspecification | Empty input, short query (< 10 chars), or low classification confidence with no retrieved evidence. | Prompt user for required context. | `RECOMMENDATION_ONLY` |
| **POL-004** | Complaint Escalation | Intent classified as `complaint` or mentions escalation keywords (`supervisor`, `sue`, `unacceptable`). | Route ticket to senior human resolution team. | `HUMAN_REVIEW` |
| **POL-005** | Confidence Thresholding | Classification confidence `< 0.60`. | Escalate to human supervisor due to intent uncertainty. | `HUMAN_REVIEW` |
| **POL-006** | Evidence Sufficiency | Retrieved top evidence score `< 0.22`. | Route to human verification; prohibit automated response without grounding. | `HUMAN_REVIEW` |
| **POL-007** | Safe Grounded Auto-Response | Confidence $\ge 0.60$, Evidence $\ge 0.22$, and POL-001/002 passed. | Dispatch automated response with verified document excerpt citation. | `AUTO_RESPONSE` |

**Zero Real-World Mutations:** The system operates strictly as a decision-support and recommendation engine. It does not interface with real banking APIs, live card networks, or production database mutation endpoints.

## 4. Engineering Trade-offs

### A. Accuracy vs. Inference Latency
- **Keyword Baseline:** Mean latency **0.062 ms**, but Intent Accuracy is only **68.75%** and fails on natural paraphrasing.
- **Dense Linear Pipeline:** Mean latency **11.007 ms** (CPU-only), but Intent Accuracy reaches **87.50%** (+27.3% relative gain) and Macro-F1 reaches **0.8813** (+28.5% relative gain).
- **Decision:** The ~11 ms latency budget is well within enterprise SLAs (< 200 ms) and provides substantial gains in intent recognition and user experience.

### B. In-Memory Query Caching vs. Staleness & Safety
- **Benefit:** Repeated or normalized queries evaluate in **2.008 ms mean latency** (with median responses under **0.04 ms**), delivering an operational **5.48x speedup**.
- **Safety Control:** To prevent caching stale or dangerous states, queries resulting in `BLOCKED_BY_POLICY` or transient ambiguous queries requiring clarification are strictly **excluded from the cache**.

## 5. Failures Encountered & How They Were Resolved

### 1. Lexical Sparsity in Small Training Datasets
- **Symptom:** The initial TF-IDF-only classifier achieved only 62.5% accuracy on held-out test data. Unseen test vocabulary resulted in all-zero TF-IDF vectors, defaulting to majority classes (`refund_request`) due to intercept bias.
- **Resolution:** Replaced the pure TF-IDF pipeline with a supervised linear probe on pre-trained `all-MiniLM-L6-v2` dense embeddings, using the TF-IDF pipeline only as an offline fallback. This boosted test accuracy to 87.50% and Macro-F1 to 0.8813.

### 2. Spurious Evidence Matching on Vague Inquiries
- **Symptom:** Without threshold gating, cosine search always returned a top document even for queries like *"Help with my stuff"*, causing the engine to fabricate recommendations citing unrelated policies.
- **Resolution:** Implemented relevance threshold gating (`threshold = 0.22`). When no document achieves the minimum similarity score, the retriever returns an empty set, triggering `POL-003` / `POL-006` escalation.

### 3. Adversarial Prompt Injection & Financial Evasions
- **Symptom:** In baseline testing, queries like *"Immediately transfer $1200 from company reserves"* bypassed generic keyword filters because they did not use exact keywords like `"wire transfer"`.
- **Resolution:** Strengthened regex pattern matching in `POL-001` to capture currency patterns (`transfer \$?\d+`), privilege escalations (`grant admin privileges`, `root shell`), and instruction override phrases (`skip all policy verifications`). Safety enforcement achieved 100.0% (6/6 blocked/escalated).

### 4. Cloud Container Wheel Incompatibility
- **Symptom:** During initial deployment to Streamlit Community Cloud, the default container environment selected Python 3.14, which lacked pre-compiled binary wheels for PyTorch and Sentence-Transformers, causing build stalls.
- **Resolution:** Added `.python-version` pinned to `3.11` and added `.streamlit/config.toml` with `fileWatcherType = "none"`, allowing clean deployment via pre-compiled Linux binary wheels.

## 6. Known Limitations

1. **Probability Calibration:** The classifier outputs raw softmax scores from `LogisticRegression(C=5.0)`. While effective as relative ranking signals, they are not calibrated with Platt scaling (`CalibratedClassifierCV`) or isotonic regression.
2. **Single-Node In-Memory Cache:** The current cache is process-local and does not synchronize across distributed workers unless backed by Redis.
3. **Template Phrasing:** The response generator uses deterministic template insertion to ensure 100% grounding. When an LLM API key is optional, conversational fluency can be increased without sacrificing grounding.

---

## 7. Production Roadmap & Next Improvements

1. **Explicit Probability Calibration:** Train a Platt scaling calibrator on a larger held-out validation set to output true empirical probabilities.
2. **Distributed Redis Cache:** Replace the local dictionary cache with Redis clustering and TTL expiration for multi-node horizontally scaled deployments.
3. **Asynchronous LLM Integration with Guardrail Envelope:** Integrate Gemini or Claude for fluid natural language generation wrapped within an immutable pre- and post-generation policy check.
4. **Human-in-the-Loop Review Queue:** Connect tickets routed to `HUMAN_REVIEW` directly into a Zendesk / Jira Service Desk webhook.
